## Headline findings from the source read

1. **The brief's file list has drifted.** `vllm/v1/worker/gpu_model_runner.py` no longer exists; the
   runner is `vllm/v1/worker/gpu/model_runner.py` (`GPUModelRunner`). Details in SOURCE_TRACE.md.
2. **There is no prefill/decode phase in the scheduler.** Each request just has `num_computed_tokens`
   chasing `num_tokens_with_spec`; chunked prefill, prefix caching and spec decode all fall out of that.
3. **Token budget and KV allocation are charged together, per request, per step**
   (`allocate_slots(request, num_new_tokens)`), and a failure charges neither. Day 3 instead reserves
   the whole prompt's KV at admission and spends the budget in a separate phase. vLLM also *checks*
   the whole prompt fits (`scheduler_reserve_full_isl`, default on) but allocates only the first
   chunk. See COMPARISON.md §2.
4. **Preemption is only ever for running requests.** A waiting request that cannot get blocks just stops
   the admission loop, and a step that preempted anything admits no new requests.
5. **`gpu_memory_utilization` is not a speed knob.** It sets the KV pool size; it matters only once
   the pool is the binding constraint. `max_num_batched_tokens` also shrinks the pool (the startup
   profile run sizes activations at that value).

Findings 3–5 are read from the code; whether they show up as measurable effects on a real GPU is
exactly what Session 3 would test.

## Limitations

- **Session 3 was never executed.** No `vllm serve` or `vllm bench serve` has been run by this code.
  `run_sweep.py`'s real subprocess path is smoke-tested with stand-in child processes and a local HTTP
  server, not with vLLM; `setup_gpu_host.sh` only fails-fast on non-Linux here. Flag names were checked
  against the v0.34.0 source, not by running them.
- **Pinned to one version.** Everything is `v0.34.0`. Interior line numbers in SOURCE_TRACE.md
  (inside function bodies) are not machine-checked; definition lines are.
- **Source-reading depth.** The scheduler, KV manager, block pool, executor, worker and runner were
  traced; multimodal, LoRA, KV-connector (P/D), hybrid-KV and data-parallel paths were noted but not
  analysed.
- **Reviewed, not battle-tested.** A code review and a security review were run on the tooling and
  their real findings fixed (resume/aggregation integrity, teardown of orphaned worker processes,
  loopback binding, port-in-use refusal, proxy bypass, NaN handling, nested-block symbol lookup).
  Low-severity items deliberately left: terminal/CSV escaping of untrusted result files, hash-locked
  dependencies, and pinning the model revision.
- **COMPARISON.md's "prediction"** (Day 3 under-estimates concurrency under chunked prefill) is untested.
- Baseline pins `--max-num-seqs 256 --max-num-batched-tokens 8192` and `--ignore-eos`, which differ from
  both vLLM's GPU-dependent defaults and the brief's literal command; see RUNBOOK.md for why.
